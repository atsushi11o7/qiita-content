## はじめに

これまで、データ分析やデータセット作成で SQL を使うことはあっても、データベースそのものを設計・運用する機会はほとんどありませんでした。

最近は RAG システムの構築でベクトル DB を使っていますが、メタデータなどを通常のデータベースで持つ場面もあります。
個人開発で使っていた DB も、正直あまりしっかり考えずに作っていました。

そこでこの機会に、DB 設計の考え方を一度まとめておくことにしました。
この記事はその学習ノートです。

設計の判断の型と、正規化などの基礎を整理していきます。

## DB 設計は何を決める作業か

<!-- メモ: 仕様を「どんなテーブルを持つか」に翻訳する作業。決めるのは主に4つ=エンティティ(登場するモノ)/関係(1対多・多対多)/不変条件(常に成り立つべきルール)/制約(それを DB で守る仕掛け)。ここが素直だと多くの機能は自然に書け、歪むと全部歪む。後から直すコストが一番高い。全体像を先に示し、以降で順に掘る。 -->

## エンティティと関係を見つける

<!-- メモ: この親直下は導入のみ。仕様の中の名詞=エンティティ候補、動詞=操作。関係の見つけ方を次の ### で。 -->

### 1 対多 / 多対多

<!-- メモ: 1対多は「多」側に外部キーを持たせる(例: ユーザー1人が記事を複数)。多対多は中間テーブルで分解(例: 記事とタグ)。多対多を中間テーブルにする理由(片側に配列で持つとクエリ・整合性が破綻)。ER 図で 1対多・多対多を対比。 -->

### 属性を持つ中間テーブル

<!-- メモ: 中間テーブル自身が属性を持つケース(注文明細=数量・単価)。単なる多対多の連結ではなく「関係の属性」を載せる。【図: 注文の ER 図 CUSTOMER/ORDER/PRODUCT/ORDER_ITEM】。ここでスナップショット(単価は注文時点の値をコピー)の伏線。 -->

## 正規化 — 更新異常を防ぐ

<!-- メモ: この親直下は導入。正規化=重複をなくして「更新異常・挿入異常・削除異常」を防ぐ手続き。1つの事実は1箇所にだけ持つ、が核。悪い例(全部1テーブルに詰め込み)から、1NF→2NF→3NF で段階的に直す。各段階で「どの異常が消えるか」を before/after のテーブル + SQL で見せる。 -->

### 第 1 正規化（繰り返し・複数値をなくす）

<!-- メモ: 1セルに複数値(カンマ区切りタグ、繰り返し列 item1/item2/item3)を排除。1セル1値・行の順序に依存しない。悪い例→分割。SQL で「タグを LIKE 検索する羽目になる」問題を示す。 -->

### 第 2 正規化（部分関数従属をなくす）

<!-- メモ: 複合主キーの一部にしか依存しない列を別テーブルへ。例: (order_id, product_id) が主キーの明細に product_name を置くと、product_id だけで決まる product_name が重複。→ 商品テーブルへ分離。更新異常(商品名変更が全明細に波及)を示す。 -->

### 第 3 正規化（推移的関数従属をなくす）

<!-- メモ: 主キー以外の列に依存する列を別テーブルへ。例: users(id, zip, city) で city は zip に従属 → zip テーブルへ。主キー→非キー→非キーの連鎖を断つ。実務では 3NF まで正規化してから必要に応じて崩す、が基本線。 -->

## あえて正規化しない — 非正規化とスナップショット

<!-- メモ: 正規化は基本だが、常に正しいわけではない。判断軸=「その重複は、元が変わったとき一緒に変わるべきか」。一緒に変わるべき→参照(正規化)。その時点で確定させたい→コピー(スナップショット/非正規化)。例: 注文明細の単価(注文時点で確定、後で商品価格が変わっても不変)。集計結果のキャッシュ列(読み高速化 vs 二重管理のトレードオフ)。非正規化は「意図してやる」もので、なんとなく重複させるのとは違う。 -->

## 制約で不変条件を守る

<!-- メモ: 不変条件はアプリ任せにせず DB 側でも守る。主キー(重複しない・NULL でない)/外部キー(存在しない親を参照させない)/UNIQUE(業務上の一意=同じユーザーが同じ URL を重複保存しない等)/CHECK(在庫≥0、金額≥0)。sqlite3 で「制約に反する INSERT が弾かれる」挙動を確かめる(PRAGMA foreign_keys=ON の注意も)。〔実験: 制約違反の再現は別リポで確認して差し込み〕 -->

## インデックスと設計

<!-- メモ: 索引=読みを速く(全走査 O(n)→索引で絞り込み)、書きは索引更新ぶん遅く、容量も増える。どの列に張るか(検索・結合・一意制約に使う列)。設計段階で「よく引く条件」を意識してキーを決める。EXPLAIN QUERY PLAN で SCAN→SEARCH USING INDEX を観察。〔実測(SCAN/SEARCH の実際の出力)は別リポで確認して差し込み〕。ただし早すぎる最適化は避ける=まず正しく設計、詰まったら索引。 -->

## やりがちなアンチパターン

<!-- メモ: EAV(entity-attribute-value: 何でも key-value で持つ→型・制約・クエリが死ぬ)。何でも JSON カラム(検索・整合性が効かない。半構造化の一部なら可、主要データを JSON に逃がすのは注意)。正規化しすぎ(結合だらけで読みにくい・遅い→適度な非正規化)。ソフトデリート(deleted_at)の罠(UNIQUE 制約と両立しない・クエリが常に WHERE deleted_at IS NULL になる・本当に論理削除が要るか)。「とりあえず id と全部 TEXT」も一言。 -->

## ケーススタディ「このデータ → こう設計」

<!-- メモ: この親直下は導入。「データの特徴 → ER 図 → 設計判断」を数本。各ケースで、どの考え方(多対多/属性中間/スナップショット/制約)が効くかを回収。 -->

### タグ付け（多対多）

<!-- メモ: 記事に複数タグ、タグは複数記事に。→ article_tags 中間テーブル((article_id, tag_id) 複合主キー、両方に FK)。タグ名は tags テーブルに一意で持つ(重複させない)。【図: ER 多対多】。「記事のタグを配列カラムで持つ」誘惑と、それが検索・整合性で破綻する理由。 -->

### 注文と明細（属性を持つ中間 + スナップショット）

<!-- メモ: 顧客・注文・商品・明細。OrderItem は属性を持つ中間(数量・単価)。単価は注文時点のスナップショット。合計は明細から導出(重複して持たない)。在庫は CHECK(stock>=0)。【図: ER】。エンティティと関係を見つける + スナップショット + 制約の総合回収。 -->

### 履歴・監査ログ（追記型）

<!-- メモ: 「いつ・誰が・何を変えたか」を残す。上書きせず追記(イミュータブル)。現在値テーブル + 履歴テーブルの二本立て、または event ログから現在値を導出。時点の値をスナップショットで持つ。論理削除より履歴の方が素直なことも。設計判断=「過去を保持する必要があるか」。 -->

## まとめ

<!-- メモ: DB 設計で決めるのはエンティティ・関係・不変条件・制約。1つの事実は1箇所に(正規化)、ただし確定させたい値はスナップショットで持つ。不変条件は DB の制約で守る。アンチパターン(EAV・何でも JSON・過剰正規化・安易なソフトデリート)を避ける。「このデータはどう持つべきか」を最初に考えると、後の実装が楽になる。 -->

## サービス開発をどう考え、どう設計するか

<!-- メモ: この章の狙い。サービスは2軸で捉えると見通しがよい=「何でできているか(段階)」と「どういう順で考えるか(設計の型)」。以降で各段階の道具を、最後に型に沿った実践を扱う、という地図を先に示す。親直下は導入のみ。 -->

### サービスを「段階」で捉える

<!-- メモ: まずデータをどう持ち→次にどう処理し→次に外部へどう公開し→さらに速く安全に大規模に保ち→最後に組み合わせて設計する。上の段は下の段に成り立つ(処理は持ち方に、公開は処理に依存)。早めのメッセージ「多くの機能はデータ構造が素直なら自然に実装できる」→データ設計が起点。【図: 段階の地図 flowchart TB S1→S5】 -->

### 設計の「型」— この記事の背骨

<!-- メモ: 思いつきで実装に飛びつくと後で全部やり直し。毎回同じ順序でたどると抜け漏れ防止&判断理由を言語化できる。型=要件確認→機能洗い出し→データ設計→構成→スケール対応→運用監視。各ステップで「何を問い何を決めるか」を具体化(要件=目的スコープ/利用者規模/読み書き比率/一貫性、やらないことを明示。機能=名詞と動詞、Must/Nice、中心1機能から。データ設計=エンティティと関係〔1対多/多対多/属性を持つ中間〕と不変条件、主キー/外部キー/一意制約、スナップショット。構成=リソースとエンドポイント、読み経路/書き経路、キャッシュ位置、まず単一構成。スケール=ボトルネック見極めてから、症状→打ち手の表。運用=何を記録・異常にどう気づく・設定値を計測で見直す)。原則: 上から順だが行き来してよい、動く核から広げる。【図: 型のフロー flowchart LR、S/C→D に見直して戻る】。症状→打ち手の表も入れる。 -->

### 段階と型はどう噛み合うか

<!-- メモ: 型の各ステップが、どの段階の道具を使うかの対応。データ設計=持ち方の段、構成=公開の段+持ち方の段(キャッシュ)、スケール対応=信頼性/規模の段、機能の中身(処理)=処理の段。対応表を1つ。 -->

### ミニ実例: ブックマーク保存を型で一巡する

<!-- メモ: 本格適用は最後の設計実践だが、小さな例で型の回し方を掴む。題材=URL とタイトルを保存/一覧/削除する個人向けブックマーク。①要件(個人が保存/一覧/削除。認証共有タグはやらない。一覧〔読み〕多め、強い一貫性不要)②機能(名詞=ブックマーク〔url,title,created_at,所有者〕、動詞=保存/一覧/削除、中心=保存→一覧)③データ設計(bookmarks(id PK,user_id FK,url,title,created_at)、1対多、不変条件=同じユーザーが同じ URL を重複保存しない→(user_id,url) に UNIQUE)④構成(POST/GET/DELETE、主に一覧の読み経路、増えたらページネーション、今はキャッシュ不要)⑤スケール(個人なら単一構成で十分、と判断できるのも設計。伸びるなら user_id でシャーディング/keyset ページネーション。「今は打たない」も結論)⑥運用(保存数・エラー率・UNIQUE 違反頻度を見て見直す)。学び=小さくても同じ順でたどると UNIQUE やページネーションが自然に出る。 -->

## まず、データをどう持つか

<!-- メモ: この段の親導入。データの持ち方=土台。モデリング→DB基礎→キャッシュの順。 -->

### データモデリング

<!-- メモ: 仕様を「どんなテーブルを持つか」に翻訳。1対多は「多」側に外部キー、多対多は中間テーブル。属性を持つ中間エンティティ(注文明細=数量・単価を持つ)。スナップショット(単価は参照でなくコピーして確定)。正規化のやりすぎ/あえて重複=「その重複は元が変わったとき一緒に変わるべきか」で判断。【図: 注文の ER 図 erDiagram CUSTOMER/ORDER/PRODUCT/ORDER_ITEM】。実装パターン: Product/OrderItem/Shop.place_order(単価コピー)/order_total(明細から導出)。使用例: 注文後に price を変えても order_total は不変。 -->

### データベースの基礎（sqlite3 で動かす）

<!-- メモ: 標準同梱の sqlite3 で実際に動かす。インデックス(無いと全走査 O(n)、索引で O(log n)、EXPLAIN QUERY PLAN で SCAN→SEARCH USING INDEX、読み速く書き遅い)。トランザクション/ACID(with conn: が境界、途中失敗で全ロールバック=原子性)。制約(外部キー/UNIQUE/CHECK で整合性を DB 側に)。実装パターン: query_plan()/add_user_with_articles(fail_at で途中失敗→巻き戻り)。 -->

### キャッシュ

<!-- メモ: 速度と引き換えに整合性の課題。Cache-Aside(見る→無ければ DB→保存)。TTL(期限で捨てる)/無効化(更新時に対応キーを消す)。読み多く更新少ないデータ向き。サンダリングハード(一斉失効で DB 殺到)→TTL をずらす。【図: Cache-Aside sequenceDiagram ヒット/ミス】。実装パターン: SimpleCache(get で期限切れ捨て/set/invalidate)、UserRepository(get_user で Cache-Aside、update_user で invalidate)。 -->

## 次に、持ったデータをどう処理するか

<!-- メモ: この段の親導入。持ったデータを処理する道具箱。多くの機能はデータ構造が素直なら自然に書ける、を体感する段。 -->

### データ構造の使い分け

<!-- メモ: 辞書=キー参照 O(1)/集合=メンバー判定 O(1)(x in list は O(n))/リスト=順序・末尾スタック(先頭 pop は O(n))/deque=両端 O(1)(キュー)。実装: has_duplicates(集合)/dedupe_preserve_order(判定=集合・順序=リスト)/Queue(deque)。 -->

### 集計

<!-- メモ: キーごとにまとめる(合計・カウント・グルーピング)。辞書が軸で O(N)。存在しないキー=get(k,0)/defaultdict/Counter。実装: sum_by_key(get(key,0))/group_by_key(defaultdict(list)、返す前に dict へ)。 -->

### ソート

<!-- メモ: sorted(key=...)。複合キーはタプル。数値降順は符号反転で一部だけ降順。安定ソート。実装: sort_by_value_desc((-値,キー))/rank(集計してから並べる)。 -->

### 探索

<!-- メモ: 線形 O(n)/二分 O(log n)(ソート済み前提)。境界探索 lower_bound(値でなく「◯◯以上が最初に現れる位置」)。半開区間 [lo,hi) で off-by-one 防止。実装: binary_search(自前)/lower_bound(判定を < に変えるだけ)。bisect を使わず自前で仕組みを見る。 -->

### 区間の処理

<!-- メモ: 「重ならない条件の否定」で判定(場合分けを増やさない)。境界の </<= は仕様で。全ペア O(N^2)→ソートして隣接比較 O(N log N)。実装: overlaps(not (e1<=s2 or e2<=s1))/has_any_overlap(ソートして隣接)/BookingManager.book。→この overlaps は後の予約システムで再利用する、と言葉で予告。 -->

### グラフ・木の探索

<!-- メモ: 隣接リスト表現。BFS(キュー、重みなし最短ホップ)/DFS(再帰)。visited 必須(閉路で無限ループ防止)。木はグラフの特殊形。O(V+E)。実装: bfs/dfs/shortest_hops(重みなし最短、到達不能は None)。 -->

## 次に、処理を外部へどう公開するか

<!-- メモ: この段の親導入。作った処理を外部から呼べる形に。HTTP→REST→リアルタイム。仕組みを自前で書いて理解する。 -->

### HTTP の基礎

<!-- メモ: HTTP はテキスト。開始行+ヘッダ+空行+ボディ。境界は空行(\r\n\r\n)。ヘッダ名は大小無視。Content-Length は本文のバイト数。実装: parse_request(空行で分割、ヘッダ小文字化)/build_response(Content-Length 自動付与)。生リクエストのパース/レスポンス生成を自前で。 -->

### REST API の設計

<!-- メモ: URL は名詞、操作はメソッド。ステータス 201/200/204/404/405(パスは在るがメソッドが無い)。べき等性(PUT は繰り返しても不変、POST は増える)。【図: 振り分けフロー flowchart パス一致?→メソッド一致?→404/405/ハンドラ】。実装: 最小 Router(add/_match で {id} 捕捉/dispatch でパス在→405・無→404)。この Router は後の設計実践で再利用、と予告。 -->

### リアルタイム通信

<!-- メモ: 更新を能動的に届ける3方式。ロングポーリング(新着まで保留、カーソルで取りこぼし防止)/SSE(一方向テキスト、空行終端)/WebSocket(双方向、ハンドシェイク)。誰が始め何往復かを図で比べる。【図×3: ロングポーリング/SSE/WebSocket の sequenceDiagram】。実装: MessageLog.poll(cursor 以降+次カーソル)/format_sse(空行終端)/websocket_accept(RFC6455 GUID で sha1→base64)。 -->

## さらに、速く・安全に・大規模に保つ

<!-- メモ: この段の親導入。動く形を、速く・安全に・大規模に。並行→レート制限→スケール→性能。ボトルネックを見極めてから打つ。 -->

### 並行処理

<!-- メモ: 競合の根本=メモリ共有。count += 1 すら「読む→足す→書く」で割り込まれると更新が消える。ロックで不可分に。【図: 更新が消える sequenceDiagram T1/T2 が両方 0 を読んで両方 1 を書く→2回増やしたのに 1】。実装: UnsafeCounter(壊れる)/SafeCounter(with self.lock で守る)。対比で見せる。 -->

### レート制限

<!-- メモ: 数える単位(API キー > IP、IP は NAT を巻き込む)。固定ウィンドウ(境界で2倍問題)/トークンバケット(バースト許容+平均制限、実務で広い)。超過は 429。実装: TokenBucketLimiter.allow(経過分を補充〔上限あり〕→1以上なら消費して許可、なければ拒否)。 -->

### スケールのパターン

<!-- メモ: ステートレス化で水平分散が楽。ロードバランサ/リードレプリカ(遅延=結果整合性)。シャーディング: hash % N はノード追加でほぼ全キー移動→コンシステントハッシュで抑制(仮想ノードで偏り減、円環上で自分以降の最初のノードを二分探索)。実装: modulo_shard/ConsistentHashRing。実測(3→4ノード,1000キー: modulo 約750移動 vs コンシステントハッシュ 約250)=数字で語る。【追加候補: コンシステントハッシュの円環を画像化(Mermaid では描きにくい)→ 清書時に用意するか要検討】。 -->

### Web パフォーマンス

<!-- メモ: まず計測(LCP 等)。サーバ側の核=条件付きリクエスト(ETag→304 で本文再送を省く)/gzip で転送量削減。実装: etag_for(内容の指紋)/handle_conditional_get(if_none_match 一致で 304)/compression_ratio(圧縮後/前、繰り返しの多いテキストは大幅に縮む)。 -->

### 設計の型を適用する

<!-- メモ: 型(要件→機能→データ設計→構成→スケール→運用)は前章で詳述済み。ここではそれを実サービスに適用。設計書形式とロードマップ形式の2通りの見せ方を説明。 -->

### ケーススタディ: URL 短縮（設計書形式で型を一巡）

<!-- メモ: 長い URL を短いコードにし、コードへのアクセスを元 URL へ転送。型の6見出しで一気に設計。①要件(短縮/解決/計測、認証・独自ドメイン・管理UIはやらない、解決〔読み〕>>発行〔書き〕なので解決経路が主戦場、発行コードは常に同じ URL へ=強い一貫性、クリック数はずれてよい)②機能(発行/解決〔中心〕/計測、名詞=コードと元URLの対応、中心=発行→解決)③データ設計(url_mapping(code PK,long_url,created_at,click_count)、肝はコードの作り方=連番ID を base62〔6文字で約568億通り〕、連番は衝突しない・短い・確定的、トレードオフ=隣を推測されやすい→秘匿要るなら乱数+衝突チェック、別解=URL ハッシュ、公開URLなので連番で十分)④構成(POST /api/urls 発行 201/GET /{code} 解決 302、パス衝突注意=catch-all /{code} と管理APIを /api/ 配下に分ける定石、前段の部品〔キャッシュ・ルータ・レート制限〕を import して配線)⑤スケール(解決経路にキャッシュ、コードでシャーディング〔コンシステントハッシュ〕、発行にレート制限、採番の分散=ノードごとに ID レンジ)⑥運用(クリック数/発行数/解決404率、クリックは非同期集計の判断も)。【図: URL短縮アーキ flowchart Client→Router→レート制限/キャッシュ→Service→DB】。実装: encode_base62/ShortenerService/UrlShortenerApp(部品の配線)。 -->

### ケーススタディ: 予約システム（ロードマップ形式）

<!-- メモ: 会議室のようなリソースを時間帯で予約。希少資源=時間帯(区間)、核=処理・並行制御。まず型で設計(①要件=予約/キャンセル/一覧、課金通知やらない、同じリソースで時間帯が重なってはいけない=強い ②機能=予約〔中心〕/キャンセル/一覧 ③データ設計=Booking(id PK,resource_id,start,end)、1対多、不変条件=同じ resource_id で区間が重ならない、判定は処理の段の overlaps を再利用 ④構成=POST /bookings 201/重なれば 409 Conflict、DELETE 204、GET 一覧 ⑤スケール=全件走査 O(N) をやめ開始時刻ソートで隣接、並行制御はリソース単位にロック範囲を閉じる、本番は DB のトランザクション・制約へ ⑥運用=成功率/409率/キャンセル率)。作った道のり=まず単純(単一リソースの重なり判定=overlaps 再利用)→広げる(複数リソース+Booking+キャンセル)→本番へ(二重予約 check-then-act をプロセス内ロックで防止+API化 409)。実装: RoomCalendar→BookingService→SafeBookingService(book/cancel をロックで包むだけ=差分はロックのみ)→make_booking_api。20スレッドが同枠を狙っても成功1件のみ。限界=プロセス内ロックは複数台で破綻→次の EC へ。 -->

### ケーススタディ: EC 在庫（ロードマップ形式）

<!-- メモ: 商品を在庫つきで扱い、複数商品をまとめて注文。希少資源=個数(在庫カウント)、核=データ設計。予約と対になるケース。型で設計(①要件=在庫管理/注文/合計、決済配送やらない、売り越さない=在庫が負にならない・注文金額確定=強い ②機能=在庫つき商品/注文〔在庫足りれば確保、1つでも足りなければ何も売らない=中心〕/合計/参照 ③データ設計★主役=Customer/Product(価格・在庫)/Order/OrderItem(数量・単価)、顧客1対多注文・注文1対多明細・商品1対多明細、OrderItem は属性を持つ中間エンティティ、不変条件=在庫≥0/合計=Σ(数量×単価) は明細から導出/単価は注文時点スナップショット ④構成=POST /orders 201/在庫不足 409、GET /products/{id} ⑤スケール=在庫を別テーブル・行ロックで競合範囲を狭める、商品IDでシャーディング、カート=予約在庫〔TTL 付き hold〕 ⑥運用=成功率/在庫不足409率/在庫切れ商品)。作った道のり=まず単純(単一商品 在庫≥0)→中心(注文/明細を厳密にデータ設計、全明細を確認してから減らす=原子性の芽)→本番へ(sqlite で実DB化、CHECK+条件付き減算 UPDATE...WHERE stock>=? +トランザクションで売り越し防止+API化)。【図: place_order 分岐 flowchart トランザクション→条件付き減算→更新0行?→全ロールバック409/スナップショット→残り?→commit201】。実装: Inventory.buy→Shop.place_order(メモリ版、確認してから減らす)→OrderDB.place_order(条件付き減算+rowcount==0 で InsufficientStock+スナップショット)。 -->

### 予約と EC の対比

<!-- メモ: 記事に必ず入れる対比表。予約=希少資源:時間帯(区間)/核:区間の重なり・並行制御/並行制御:プロセス内ロック/主に関わる段:処理の段・信頼性の段。EC=希少資源:個数(カウント)/核:データ設計(関係・不変条件)/並行制御:DB のトランザクション+制約/主に関わる段:持ち方の段。メッセージ=「守りたい不変条件は何か」を見極めるとモデリングも処理も自然に決まる。時間の希少性と個数の希少性という2典型。 -->
